# MidoriVPN browser extension 2.0.0

Firefox and Chromium extension that routes browser traffic through an authenticated HTTPS CONNECT gateway. It is a browser proxy client, not a device-wide WireGuard client.

## Release status

| Category | Current state |
|---|---|
| Implemented | OAuth/PKCE, encrypted session storage, fail-closed proxy runtime and separate Firefox/Midori and Chromium bundles are present and covered by repository checks. |
| Certified | Existing browser E2E and package-lint evidence is tied to the tested environment and exact candidate; it does not mean the current source is store-published. |
| Pending | 2.0.0 remains **Unreleased**. Final reproducible packages, store review and independent regional proxy validation remain separate gates. |

## Security properties

- OAuth 2.0 Authorization Code + PKCE with strict callback origin, path and
  state validation; simultaneous sign-in flows retain independent, bounded
  verifier transactions.
- Access/refresh tokens encrypted with AES-GCM using a non-extractable key stored by IndexedDB; no password-derived or cleartext persistence fallback.
- Production CSP denies every source by default and permits configured API,
  identity and explicit regional health-probe origins. Set `EDGE_PROBE_ORIGINS`
  to every independent Core origin used by this build, comma separated, HTTPS
  only and without paths or wildcards. A new regional origin requires a new
  validated extension build; the API cannot broaden CSP dynamically.
- Logout clears account data and pending OAuth flows without rotating the
  installation UUID. Download suggestions do not inspect GPU identifiers or
  request high-entropy browser client hints.
- Proxy routing is available only when the selected server advertises an enabled, healthy normalized `proxy` transport.
- Automatic mode requests the fail-closed `proxy` candidate contract, requires
  three successful HTTPS health probes per candidate and chooses the lowest
  median RTT. Manual mode remains pinned to the selected server.
- There is no implicit host, scheme or port fallback.
- Proxy authentication uses a short-lived `vpn-proxy` token; a general OAuth access token is never sent to the proxy.
- Missing credentials/permissions/configuration fail closed through a loopback black-hole proxy instead of leaking traffic directly while the VPN toggle is on.
- Three nearby proxy errors start recovery. Retry state and bounded
  5/10/20/40/60-second backoff survive service-worker restarts; isolated
  errors do not accumulate indefinitely.

## Rootless development

Create the local `.env` from `.env.example`; never commit client IDs, callback
origins or API endpoints that belong only to a deployment. The pinned rootless
runner discovers this repository either below the Core checkout or beside it.
Point `CORE_REPO` at Core with an absolute path, then run from this directory:

```bash
CORE_REPO=/absolute/path/to/midori-vpn-core
bash "$CORE_REPO/scripts/pod.sh" npm ci
bash "$CORE_REPO/scripts/pod.sh" npm run check
bash "$CORE_REPO/scripts/pod.sh" npm audit --audit-level=high
```

The check runs strict type checking, lint with zero warnings, the gate against
programmatic popup opening, unit tests and both production bundles.

Build one browser explicitly:

```bash
bash "$CORE_REPO/scripts/pod.sh" npm run build:firefox
bash "$CORE_REPO/scripts/pod.sh" npm run build:chrome
```

ZIP artifacts are generated by the production Webpack configuration. Load only the matching browser output when testing; Firefox and Chromium manifests have different proxy/auth capabilities.

## Store release preparation

`npm run release:build` creates deterministic Firefox/Midori and Chromium ZIPs,
the AMO reviewer source archive, store metadata, SPDX documents, provenance and
checksums. Firefox is validated with the exact latest compatible `web-ext`
version in the lockfile. Its current upstream image parser is preloaded with
ICNS, JXL and HEIF disabled because MidoriVPN store assets are PNG and those
unused parsers were historically affected by denial-of-service advisories. The
locked version is patched; the restriction remains defense in depth. A directed test
must pass before linting. Errors and unreviewed warnings fail the build; the
narrow reviewed allowlist is documented in
`scripts/lint-firefox-package.sh`.

Store submission is deliberately separate from building. See
`docs/STORE_RELEASE.md` for the protected AMO and Chrome Web Store gates. Those
commands require operator-provided credentials and explicit confirmation; a
normal build never uploads or publishes anything.

## Runtime flow

1. The background worker restores the encrypted OAuth session.
2. `/api/v1/control/servers` supplies manual choices. Automatic mode uses
   `/api/v1/control/servers/candidates?protocol=proxy` and measures only its
   validated HTTPS health endpoints.
3. The user keeps automatic selection or pins a manual server, then enables
   browser proxy mode.
4. The extension reuses one private installation UUID and sends it with the
   selected server to `/api/v1/control/proxy-credentials`.
5. Control returns one opaque regional credential bound to that user,
   installation, server, cluster and the `vpn-proxy` audience. The extension
   never parses or decodes its format.
6. Browser proxy APIs receive the normalized TLS host/port and authenticate CONNECT requests.
7. A `407` triggers a throttled scoped-token refresh. Three consecutive proxy
   failures trigger automatic recovery; with no reachable edge, browser
   traffic remains blocked while a durable alarm applies bounded backoff.
8. Definitive authentication or permission revocation disables the session;
   explicit disconnect cancels recovery and restores direct mode.
